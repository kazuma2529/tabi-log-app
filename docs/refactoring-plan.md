# リファクタリング計画

## 目的

現在の機能・画面・課金挙動を一切変えず、今後の修正箇所と責務を見つけやすくする。

## 原則

- 挙動変更を伴う修正は行わない。
- 現在の未コミット変更を尊重し、無関係な箇所は触らない。
- 一度に大きく変更せず、各段階で型チェックと lint を通す。
- 抽象化は、実際の重複または責務過多を解消する場合だけ追加する。
- アプリ起動・画面確認は、ユーザーから依頼された場合だけ行う。

## 現状監査

### 優先して整理する箇所

1. RevenueCat 接続前に使っていた未参照コードが残っている。
2. `AppScreen` がスクロールレイアウトと背景描画の両方を担当している。
3. `PremiumUpgradeCard` がカード全体と特典行の描画を同時に担当している。
4. `TravelProvider` の購入・復元後処理に同一の保存・再読込処理がある。

### 今回は触らない箇所

- `useAddVisitForm`
  - 300 行と大きいが、訪問追加フロー全体の状態遷移を担うため、分割には回帰リスクがある。
- DB の CRUD 関数群
  - 現在の責務分割はテーブル単位で明確。機能変更なしの整理効果が小さい。
- 国詳細・写真管理の操作フック
  - 操作確認なしで分割すると、ドラッグ・削除・復元動作への影響を検出しにくい。

## 実施手順

### Phase A：未参照コードの削除

- RevenueCat 接続前の案内関数と文言を削除する。
- 参照がゼロであることを検索で確認する。

検証：

- `npm run check`
- `git diff --check`

### Phase B：表示責務の分割

- `AppScreen` から背景描画を `TravelBackdrop` に分離する。
- `PremiumUpgradeCard` から特典行を `PremiumBenefitRow` に分離する。
- 表示内容、スタイル値、購入・復元処理は変更しない。

検証：

- `npm run check`
- `git diff --check`

### Phase C：購入・復元後処理の集約

- RevenueCat の購入・復元後に行う SQLite 保存と再読込を共通化する。
- 購入処理と復元処理の呼び出し先は分けたまま維持する。

検証：

- `npm run check`
- `git diff --check`

## 今後の候補

次回以降、実機操作確認とセットで以下を進める。

1. `useAddVisitForm` を国選択・詳細入力・保存処理に段階分割する。
2. 国詳細画面の編集処理を責務ごとに整理する。
3. 写真管理画面のドラッグ・削除・復元処理にテスト可能な境界を作る。
4. 自動テスト基盤を導入し、主要な selector と課金制限判定をテストする。

## リスク

- 現在は自動テスト基盤がなく、静的検証は型チェックと lint が中心となる。
- UI 部品の分割では、コード上の値を完全に維持しても実機表示の最終確認は別途必要になる。
